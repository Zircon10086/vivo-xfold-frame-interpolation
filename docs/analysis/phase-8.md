# 阶段八：KernelSU WebUI 管理界面（v1.3.0）

用户实测确认 2 倍插帧生效后，把「每个游戏单独配置」搬进 KernelSU 模块卡片的入口。v1.2 的第一版本暴露了两个问题，v1.3 按用户反馈重做：

| v1.2 | v1.3 |
|---|---|
| 列出 GameCube 预置的「已支持游戏」 | 改成「导入应用」+「管理当前应用」，只认本机装了的应用 |
| 每次写库都 `am force-stop com.vivo.gamecube` | 写库不再停 GC（见下），改完提示「重进游戏 / 点重启助手」 |
| 操作期间界面被同步命令拖住 | 所有操作进串行队列异步执行，页面底部显示任务状态条 |
| 没有清理逻辑 | 进入页面自动删除「数据库里有、本机没装」的预置游戏行（有备份） |

## 一、入口机制（已核实并跑通）

ReSukiSU（管理器 `com.resukisu.resukisu`，ksud 4.2.0-rc3，API 102）沿用 KernelSU 的模块 WebUI 规范：

- 模块根目录放 `webroot/index.html`，管理器用 WebView 打开它；
- 模块卡片左下角出现入口按钮（本机：单按钮；有 `action.sh` 的模块会多一个 ▶）；
- 页面 JS 通过管理器注入的 `ksu` 对象交互：
  - `ksu.exec(cmd, "{}", cbName)` → `window[cbName](errno, stdout, stderr)`，root 执行；
  - `ksu.getPackagesInfo(JSON.stringify(pkgs))` → 返回 `{packageName,label,...}`，用来显示应用名；
  - `ksu.toast(msg)`、`ksu.fullScreen(bool)`；
- 深链 `kernelsu://webui/<id>` 未注册给第三方 `am`，只能从管理器进。

三个坑（都踩过并解决）：

1. 手工放进 `/data/adb/modules/` 的模块，文件上下文是 `u:object_r:adb_data_file:s0` → 管理器扫不到 WebUI；`chcon -R u:object_r:system_file:s0` 后入口出现。
2. 脚本 CRLF 会让 Android `sh` 报 `set: -: unknown option`，必须 LF。
3. `sqlite3 "$DB" "pragma busy_timeout=8000; <SQL>"` 会把 pragma 的返回值 8000 打印出来，被我 `$( )` 捕获后污染比较；改成 `printf '.timeout 8000\n%s\n' | sqlite3`。

## 二、为什么之前会「卡住」

旧实现每次写库前都 `am force-stop com.vivo.gamecube`，这等于把游戏助手整棵树（含覆盖层窗口）撕掉再让它重启，单次 1~3 秒；如果管理器把 `ksu.exec` 的回调桥放在主线程，就会整页卡死。

实测证明**根本不需要停 GC**：GameCube 只是常驻持有 SQLite 连接，写操作带上 `busy_timeout` 后只要 ~50ms：

```
gc_pid=3327
rc=0 elapsed_ms=52      ← GC 运行中，带 .timeout 8000 的单条 UPDATE
```

所以 v1.3 的写入路径：`sqlite3` + `.timeout 8000`，失败才报错；是否重启 GameCube 由用户点「重启游戏助手」决定。

## 三、界面（截图：`reports/evidence/07`、`08`、`09`）

1. **状态区**：能力 / 声明 / 请求值 / 生效值 +「重启游戏助手」「重新应用能力」「刷新」。
2. **导入应用**（虚线卡片）：全屏面板列出**全部已安装应用**（含系统应用，本机 428 个），带真实应用名，可搜索；已导入的显示「已导入」。
3. **管理当前应用**：只列「已配置且已安装」的应用，每行：名称 / 包名、档位下拉（60→120、30→60）、省电插帧 / 超分 / 视效增强三个胶囊、移除。
4. 底部任务状态条 + toast：所有写操作串行进队，界面不阻塞。

## 四、数据模型变化

- 旧的「预置白名单」不再作为展示来源；数据库从「预先写好所有游戏」变成「用户导入什么就有什么」。
- **进入页面自动 prune**：删除 `game_dimen` 里所有「本机没安装」的包（整包删除，不限于本工具管理的函数），并先把 DB 备份到 `/data/local/tmp/vivo-memc-backup/`。
  - 实测：一次清掉 564 个未安装包；当前 DB 只剩 `com.miHoYo.Nap`(7 行)、`com.miHoYo.Yuanshen`(18 行)、`com.miHoYo.hkrpg`(7 行)。
  - 安全阀：`pm list packages` 结果少于 50 条时中止，避免误删全库。
- 导入一个应用 = 写 `boost_frame` + `optimize_power` + `boost_frame_v3_60_120`（`game_index=9`）；档位切换会重排 v3 行；胶囊开关增删对应函数行。

## 六、已知限制 / 下一步

1. **系统应用故意不设黑名单**（按用户要求）：导入系统应用不会崩，但没有意义；后续实测遇到不兼容再按包名加黑名单。
2. **超分 / 视效增强入口未逐项验证**：加行只代表「允许」，侧栏是否出现入口取决于 GameCube。
3. **档位只有 60→120 / 30→60**：系统 `computeUsecaseForGame` 只认这两组能到 120/60；45→90 需要原生 45 帧（本机走 -100 分支到不了），48/72→144 面板不支持。
4. **prune 是破坏性操作**：删的是 GameCube 的预置行，如果以后想恢复某个未安装游戏的官方配置，只能靠备份或重装 GameCube。
5. 模块仍是手工放目录（已给 `dist/vivo-game-memc-v1.3.0.zip`，走管理器安装可省掉上下文那一步）。

## 七、v1.4：按实测反馈修的一轮

| 反馈 | 处理 |
|---|---|
| 改档位（60→120 / 30→60）必须重启游戏助手才生效 | `set-mode` 末尾直接 `am force-stop com.vivo.gamecube`，界面 toast 提示「档位已保存，游戏助手已重启」；因为走异步队列，不再卡界面 |

| 导入的应用显示包名而不是应用名 | 导入时把 `ksu.getPackagesInfo` 拿到的 label 一起传给后端写成 `game_dimen.label`；进入页面时对历史数据做一次 `set-label` 回填 |
| 超分没有入口 | 从界面移除该开关（后端 `set-flag sr` 仍保留，便于以后验证） |
| 视效增强无论开关都显示且可用（对所有加入魔盒的 APP 全局生效） | 改为固定标签「视效增强 默认开启」，不再提供开关；`set-mode` / `add` 都会确保 `screen_light_effect` 行存在 |
| 档位选择框先出现在左上角再瞬移 | 放弃原生 `<select>`，改成页内三段按钮（60→120 / 30→60 / 自适应），没有系统弹层就没有错位动画 |

补充说明：相机这类系统应用能正常插帧（用户实测预览从 30fps 提到 120fps），说明「系统应用一律不行」不成立，取决于它是否允许悬浮窗；所以用「默认隐藏 + 可手动展开」而不是硬黑名单。

## 八、调研：能不能同时启用 60→120 与 30→60

结论：**配置层可以同时存在，但同一时刻只会有一个档生效；不存在「两个档并行」**。

依据（`e9/i.java` 的 `b()`）：

- `support_sdk = 0`（QSuperFrameView 传 `-100`）时，`i10 == -100` 让三段 `if` 全部执行，
  最后执行的是 30 段：`i12 = k.c(30_60) ? 60 : k.b(30_120) ? 120 : i12`。
  只要库里有 `boost_frame_v3_30_60`，结果就被压成 60 —— 60_120 在不在都一样。
- `support_sdk ≠ 0` 时，GameCube 传的是它测到的原生帧率（`i.c()` 读 `sp_game_fps_origin`），
  三段里只有匹配的那一段执行：60fps 走 `60_120`，30fps 走 `30_60`。

实测（v1.4 的「自适应」档，把两行都写进去并把 `boost_frame.support_sdk` 置 1）：

```
绝区零  dual：boost_frame_v3_30_60 + boost_frame_v3_60_120 + support_sdk=1
启动游戏后 settings get system gamecube_frame_interpolation
→ 1:9:25039:30:60      （菜单场景实测原生 30 帧，于是选了 30→60）
gamecube_memc_effective = 30
```

也就是说，两行同时存在时它按「当时测到的帧率」选档；绝区零菜单 30 帧就落到 30→60，反而比固定 60→120 差。所以：

- 固定档（60→120 / 30→60）：优先用，行为可预期；
- 自适应（dual）：只适合帧率会变、且希望跟着变的场景（例如相机预览 30 帧、视频 30/60 混合）；
- 想让两个提示同时出现在面板里 —— 面板文案由返回值 `[1]` 决定，一次只能显示一个目标帧率，做不到两个并列。

## 九、v1.5：三档同时可见（关键发现）

用户反馈「记得以前能同时切 关闭 / 60-120 / 30-60」，查代码后确认可行，根因是我们少写了一行。

### 第三档（优化功耗）为什么之前不出现

`FrameInterViewV3` 里三个 radio 的可见性：

- 关闭（`rb_close`）：常驻；
- 提升帧率（`rb_boost_frame`）：`this.D.f(pkg)` → `e9.k.b/c/d/e/f/g/h/i` 任一命中；
- **优化功耗（`rb_opti_power`）：`this.D.g(pkg)` → `frameinterpolation.k.u(pkg)`**，
  而 `u()` 的实现是 `e9.k.k(pkg) || e9.k.l(pkg) || e9.k.j(pkg)` —— 对应
  `optimize_power_v3_60_30_60` / `optimize_power_v3_90_45_90` / `optimize_power_v3_120_60_120` 三行。

我们之前只写了 `optimize_power`（功能开关行），**没写 `optimize_power_v3_60_30_60`**，所以第三个 radio 一直 `visibility=8`。

写入这一行之后（v1.5 的 `add` / `set-mode 60-120` 都会写）：

```
绝区零 面板出现三档：原始帧率 / 提升帧率 / 优化功耗
选「优化功耗」→ 1:9:22912:30:60   gamecube_memc_effective=30
切回「提升帧率」→ 1:9:22912:60:120 gamecube_memc_effective=60
```

即：**关闭 / 60→120 / 30→60 三个档位在同一面板里并存**，不需要模块提供档位切换。

### 由此做的精简

- 删掉 WebUI 里的档位分段按钮（改由游戏内面板选，模块只保证三行齐全）；
- 删掉「省电插帧」开关（它对应的 `optimize_power` 行现在恒开，而且原来关掉后 `set-mode` 又会自动补回来，本来就没意义）；
- 删掉「视效增强 默认开启」标签（全局行为，不需要展示）；
- 删掉「自适应」档：实测 `support_sdk=1` 时 GameCube 读 `sp_game_fps_origin`，绝区零一直按 30 帧算，
  自适应反而把 60 帧游戏降成 30→60；
- 「管理当前应用」每张卡只剩应用名 / 包名 / 移除 + 一行提示「在游戏侧栏切换」。

### 现在的数据模型（每个导入的应用）

| function | 作用 |
|---|---|
| `boost_frame` | 开启插帧功能位（`game_index=9`） |
| `boost_frame_v3_60_120` | 提升帧率 = 60→120 |
| `optimize_power` | 优化功耗功能位 |
| `optimize_power_v3_60_30_60` | 优化功耗 = 30→60（同时让第三个 radio 出现） |
| `screen_light_effect` | 视效增强（全局，无需界面开关） |

不需要 `boost_frame_v3_30_60`（那是"提升帧率"分支里的 30 帧段，会覆盖 60→120）。
